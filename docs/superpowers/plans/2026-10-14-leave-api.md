# Leave from the API (Phase 1e) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** In API mode the profile page's leave section shows a person's real leave requests, balance and leave notices, and adding, approving and rejecting leave go to the backend.

**Architecture:** `server.get('leave' | 'notifications')` and the `leave.*` commands go to `app/src/api/http/leave.ts`. The leave section reads its types, main type, allowance and balance from one hook (`useLeaveBook`): the design's fixed values in mock mode, the backend's leave types and balance in API mode. The backend gains applying on someone's behalf and admin self-approval.

**Tech Stack:** React 19, TanStack Query 5, Vitest 4. Backend: Express 5, Mongoose 9, Zod, Vitest.

**Spec:** the user's answers on 14 Oct 2026: leave types → "Backend's types"; applying → "Allow on behalf"; approvals → "Design's rules" (admins may approve their own leave). Constraints in memory: `no-ui-changes`, `api-branch-separate`, `backend-integration-plan`.

## Global Constraints

- Branch `feat/api-sign-in`; no visual UI change (labels and lists may show the backend's data); mock mode unchanged; e2e baseline 308 / DO-18, DO-19 / 3 skipped.
- Shared Demo DB: leave writes change real balances. Hands-on uses an unlimited type (Work from home) on a future date and cancels it afterwards.
- Safe dev mode (no Slack, push, email); in-app notification rows are still written.

## Decisions

1. Types: the backend's active leave types (Casual, Sick, Work from home, Comp-off…). The main type for the balance boxes is the first limited, non-earned type (Casual); its allowance is allocated + carried forward + adjusted.
2. Applying on behalf (backend `user_id` on apply): an admin for anyone, a manager or team lead for a direct report; otherwise refused.
3. Approvals: an admin may approve or reject their own request; managers only their direct reports and never their own (backend rules otherwise unchanged).
4. The backend requires a reason: an empty reason sends the type's name. Rejecting requires remarks: the app sends "Rejected by <name>".
5. Cancelled requests are not shown (the design has no Cancelled state). Leave notices on the profile are built from the person's decided requests (the backend's notifications are readable only by their owner).

## Tasks

1. Backend: apply on behalf + admin self-approval (+ tests). Commit `Backend: apply leave on someone's behalf; admins may approve their own leave`.
2. App: leave ids and types become strings (DB version 8); `useLeaveBook` (mock = today's behaviour). Commit `Leave types and balance come from one place`.
3. App: `http/leave.ts` — read requests (all for admins, own for others), notices, types and balance; write `leave.create` / `leave.decide` (+ tests); `server` + `queries` wiring. Commit `Leave through the API`.
4. Hands-on and README; final review.
